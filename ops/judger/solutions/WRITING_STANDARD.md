# 算法题库题解编写规范（版本 1）

适用当前 75 道题。使用 manifest.json 的实际题面和平台接口约定；以 source-problems/<slug>.json 为唯一事实来源。面向刚开始学习编程的读者，说明术语、下标、变量、输入输出和每一步为什么要这样做。避免宣传语、表情符号和套话。解释必须对应实际参考实现，而非声称使用另一种更快的算法。

## 统一结构

每篇必须依序包含以下八节，标题和 key 固定：

1. understand / 读懂题目：用自己的话解释任务、输入输出及平台特有约定；说明新术语，给出小例子。
2. approach / 解法思路：直观做法、核心观察、实际采用的算法；较复杂题说明如何从简单方法改进。不能把 C/Rust 的模拟实现说成真实链表实现。
3. walkthrough / 样例推演：用题面公开样例或额外明确的小例子逐步列出变量变化、状态、结果。至少三步或一张有三行以上的表格；单次四则运算题可以用读入、计算、输出三步。不得引用隐藏测试数据。
4. steps / 实现步骤：按读入、初始化、核心处理、输出组织；解释参考程序关键变量（包括 v0/v1 这类原实现变量）、下标和循环范围。
5. correctness / 为什么正确：用普通话说明关键不变量、每一步如何维护以及结束时为何得到答案。递归、DP、贪心和搜索必须给出实际理由，不写“显然正确”。
6. complexity / 复杂度：先解释 n/m 等量含义，再分别给时间、额外空间，并解释大 O 含义。以实际五语言实现为准，区别语言实现导致的差异；原生成代码中的双重循环、线性查找和排序不可冒充更快算法。输入存储与算法额外空间区别写清楚。
7. pitfalls / 边界与常见错误：至少三项具体情况，结合空值、端点、溢出、重复、初始化、下标等实际题意，不要求不存在的输入。
8. review / 复盘练习：简短总结关键观察，给出 1–2 个可自行手算的练习及答案/提示。

summary 为一句具体的算法概述。简单题正文通常 500–900 中文字以上；复杂题通常 1000–1800 中文字以上。重在充分解释，不为凑字数重复。

## 五语言代码

codes 以模式分组：{"STDIO":{"c":"...","cpp":"...","java":"...","python":"...","rust":"..."},"FUNCTION":{...}}。只写平台实际支持的模式，每个支持模式必须齐全 C、C++、Java、Python、Rust 五语言；不能漏掉仅 FUNCTION 题。

优先直接使用已经通过判题的 references[language][mode]，只加入注释和改善排版。不得更改算法、常量、数组大小、函数签名、输出协议或输入约定。若确需修改，必须说明且重新完整验证。每份代码至少在输入/函数参数、关键循环/判断/状态、输出/返回三个位置添加有针对性的中文注释；不是仅在顶部附加说明。注释说明“为什么”，避免每行无意义地翻译代码。保留合法 Main/Solution 入口和 Rust/函数驱动约定，禁止外部库。Python 注释不改变缩进。C/Java/Rust 字符串内内容不可改动。

正文中不要粘贴五份完整代码、不要使用大段代码围栏；统一由页面的代码面板显示，语言标签放在代码块顶部内部，模式可切换，带语法高亮、复制和可见的代码注释。正文只用行内代码或短伪代码解释。

## 图解

复杂算法（滑动窗口、双指针、二分、树/链表、DP、单调队列/栈、回溯、图与并查集）在 walkthrough 添加一张与推演相符的 SVG。简单算术无须装饰图。SVG 建议 viewBox="0 0 720 300"，白或浅蓝背景，蓝色 #3267b1 表示处理步骤，绿色 #26816b 表示选中/完成，琥珀 #b77930 表示待处理。字体 14–18 px，节点间留足空间，每张图附 caption 描述图中的数据及重点。图中包含明确状态/指针/路径/表格，不能只用“输入→算法→输出”充数。

仅允许 svg/g/rect/circle/ellipse/line/polyline/polygon/path/text/tspan/defs/marker/title/desc，属性仅限 viewBox、几何坐标、颜色、描边、字体、文字对齐、transform、marker-*、id、xmlns、role、aria-label。不得使用脚本、事件、style、foreignObject、image、use、a、动画、外链、内嵌位图、HTML、DOCTYPE、实体或 url()。箭头可用 polygon 显式绘制，避免 marker 引用。SVG 按需由鉴权题解接口返回，不能放到前端 public 目录泄露比赛答案。

## 文件格式与归属

每题单独写入 documents/<slug>.json，UTF-8，格式如下（不加 Markdown 围栏）：

{"schemaVersion":1,"problemSlug":"...","problemRevision":1,"title":"...","summary":"...","sections":[{"key":"understand","title":"读懂题目","markdown":"..."},{"key":"approach","title":"解法思路","markdown":"..."},{"key":"walkthrough","title":"样例推演","markdown":"...","diagram":{"caption":"...","svg":"<svg ...>...</svg>"}}, ...],"codes":{"STDIO":{"c":"...","cpp":"...","java":"...","python":"...","rust":"..."}}}

题目 revision 必须与导出的源文件一致。所有说明用 Markdown 段落、有序步骤、小表格；不用原始 HTML。source-problems 是内部核验资料，不复制 cases、profiles、references 或整个源 JSON 到题解文档额外字段。

每个 author_N 批次只修改 manifest 对应批次的 documents 文件，可自行创建本批次的生成脚本或审校记录于 authoring/author_N/。不要改应用代码、其他作者文档、题面、测试集、源文件或线上数据库，不部署、不提交、不推送。写完逐篇检查题意、样例、复杂度与代码一致，并报告完成数量、图解数量、任何需要复核的地方。
