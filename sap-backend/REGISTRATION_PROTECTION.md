# 注册防护

后端默认开启验证码和注册限额，适用于现有用户端注册页，无需第三方验证码账号。防护参数保存在现有 `sys_setting` 表，管理员可在管理端「系统设置 → 注册防护」中修改，无需修改配置文件或重启服务。

## 默认规则

| 检查 | 默认值 | 计数时机 |
| --- | --- | --- |
| 注册请求 IP 令牌桶 | 突发 20 次，持续每分钟 20 次 | 进入控制器前，非法参数、缺少或答错验证码也计数 |
| 图形验证码 | 6 位、180 秒有效、至少 1 秒后提交 | 默认每次注册必填；绑定 IP，成功或失败均一次性消费 |
| 验证码获取 | 每 IP 突发 10 次、持续 10 次/分钟；全局突发 60 次、持续 60 次/分钟 | 图片生成前；使用独立桶，不占登录额度 |
| 同 IP 注册间隔 | 10 秒 | 验证通过后、查询账号及创建用户之前 |
| 同 IP 注册额度 | 1 小时 20 次、24 小时 50 次 | 同上 |
| 同 QQ 注册额度 | 24 小时 3 次，换 IP 仍计数 | 同上 |
| 全站注册额度 | 1 分钟 30 次 | 同上 |
| 同时进行的注册 | 每实例最多 4 个，同 IP 最多 1 个 | 非阻塞拒绝，数据库调用结束或失败时释放 |

注册额度使用从首次提交开始的固定时长窗口，不按整点或午夜重置。逐项原子预占，后续检查或数据库操作失败时已占用的额度不退回，避免并发和重复失败绕过限制。拒绝请求不会延长已有窗口。

校园网可能共用出口 IP。集中招新时可根据实际人数调整 IP 额度与间隔，并保留验证码、QQ 额度和全站限制。

## 接口约定

1. `POST /api/auth/register` 提交现有注册信息。缺少验证码时返回 `code=200, data={"captchaRequired":true}`，此时尚未创建用户。
2. `GET /api/auth/captcha` 返回 `captchaId` 和 `image`（base64 图片），响应禁止缓存，服务端不返回答案。
3. 从相同来源 IP 再次提交注册信息，附带 `captchaId` 和 `captchaCode`。
4. 验证失败返回业务 `code=400`，刷新图片后重试；超出额度或并发上限返回业务 `code=429`；只有 `data="注册成功"` 表示完成。

继续沿用本项目的 HTTP 200 + 业务 code 约定。密码找回仍使用同一验证码接口，同样校验来源 IP。

## 数据库与管理端配置

超级管理员、社长（角色 `0`、`1`）可以查看和修改防护配置。页面提供验证码、注册额度与并发、请求频率三个分组，以及可信代理 IP 配置。实际值和推荐值由后端返回；「填入推荐值」仅修改页面草稿，点击保存后才生效。加载失败时显示错误并允许重试，不使用本地默认值冒充数据库配置。

| 设置键 | 内容 |
| --- | --- |
| `registration_protection_captcha` | 验证码开关、免验证额度与窗口、位数、有效期、最短作答时间 |
| `registration_protection_quotas` | 额度开关、IP 间隔、IP/QQ/全站额度、总并发及同 IP 并发 |
| `registration_protection_requests` | 请求限流开关、注册及验证码获取的瞬时容量和持续速率 |
| `registration_protection_trusted_proxies` | 可信代理 IP，以逗号或空白分隔，可留空 |
| `registration_protection_revision` | 配置版本，防止多人同时编辑互相覆盖 |

应用启动时自动补齐缺失的设置行，不需要手工执行 SQL；已有值不会被启动默认值覆盖。分组 JSON 限制在现有字段的 500 字符以内。首次没有完整合法配置时，后端初始化失败；已有有效快照后若数据库短暂不可用或配置损坏，则继续使用最后有效版本并记录日志。

- `GET /api/setting/registration-protection` 强制读取数据库，返回 `{revision, config, defaults}`。
- `PUT /api/setting/registration-protection` 接收 `{revision, config}`，校验整组参数及代理地址，在同一事务内锁定版本行并保存。旧版本返回业务 `409`，参数错误返回 `400`，不会部分保存。
- 通用设置读写接口禁止访问 `registration_protection_` 前缀，避免绕过权限、参数校验和版本检查。

保存事务提交后，本实例下一次请求重新读取数据库；其他实例最迟在下一次 5 秒缓存检查时同步。每个请求使用同一份不可变配置快照。

三个防护开关独立生效。关闭注册验证码不影响密码找回验证；验证码位数、有效期、最短作答时间和图片获取限流由两者共用。免验证次数设为 `0` 表示每次注册都验证，正数则在判断时原子预占，失败注册也消耗豁免。注册额度和请求限流不再受旧 `app.ratelimit.enabled`、`dry-run` 开关影响。

保存配置保留已有计数与在途并发。调整额度后按新的上限判断；已经开始的固定窗口、豁免窗口仍保留原到期时间。已签发的验证码继续按签发时的作答时间和到期时间校验，新图片使用新参数。降低并发上限时不会中断正在进行的注册，会限制后续请求。

旧 `app.register`、`app.ratelimit.register/captcha/captcha-global`、`app.security.trusted-proxies` 及对应环境变量不再作为这些注册防护参数的运行时来源，请统一通过管理端维护。

## 代理与存储

仅对管理端「可信代理配置」中列出的确切代理 IP 采信转发头，初始值为 `127.0.0.1,::1`，适配一体化镜像内的 nginx。独立代理需配置其实际连接后端的 IP，并覆盖 `X-Real-IP` 或在 `X-Forwarded-For` 末尾追加真实对端。留空表示不信任代理头。直连后端时伪造这些请求头不能改变限流来源。IPv4/IPv6 等价文本会归一化，变更同时影响使用 `IpUtil` 的其他接口。

注册窗口限额复用现有 Redis，Lua 原子扣减，跨实例共享；Redis 持久性取决于部署的持久化配置。Redis 不可用时沿用现有限流器的内存降级，并记录告警：此时额度仅在本实例有效，切换存储可能获得一轮新额度，进程重启后重置。内存窗口有数量上限且仅在自身到期后清理，不会空闲五分钟就重置日额度。

验证码及可选豁免计数存于本实例内存，设置数量上限并定期清理。多实例须使用粘性会话；重启后需刷新验证码。实例并发上限也仅在本实例执行。图形验证与限额用于提高自动注册成本，不能证明学号或 QQ 归属，也不能完全阻止 OCR 或人工代答。

## App 注册 QQ 邮箱验证

Web 继续使用 `/api/auth/register`，其图形验证码和防护配置保持独立。App 使用：

1. `POST /api/auth/app/register/email-code`：传学号、姓名、QQ；返回 `captchaRequired` 时，加载 `/api/auth/captcha`，补充 `captchaId`、`captchaCode` 后重新申请。发信始终要求图形验证，发送请求不携带密码。
2. 收件地址严格为本次 `QQ号@qq.com`。返回 `requestId`、邮箱、180 秒申请间隔和 900 秒有效期，不返回验证码。
3. `POST /api/auth/app/register`：基本注册字段加 `emailRequestId`、六位 `emailCode`。校验通过后仍执行现有注册准入规则并创建账号，注册成功钩子保持一致。

`sys_app_registration_code` 保存学号、QQ、IP 和验证码的 HMAC 摘要、有效期、尝试次数和消费状态。验证码绑定学号和 QQ，最多尝试 5 次；新申请使相同学号或 QQ 的旧验证码失效。错误尝试必须提交事务，账号创建和正确验证码消费在同一事务内。多个实例共享数据库锁和额度，重启不清空冷却时间。

同学号或 QQ 每天最多申请 5 次；同 IP 每小时 10 次、每天 30 次；全站每小时 30 次、每天 200 次。队列积压达到 5 封暂停新申请，使用统一邮件队列的 65 秒发送间隔。新钩子 `APP_REGISTRATION_CODE` 与模板 `app.registration-code` 首次启动自动安装并绑定，保留管理员后续编辑、停用、删除和解绑。验证码邮件到期不发送、失败详情不显示正文、不允许重发旧验证码。

接口不记录包含密码或验证码的操作日志。`ops/app-registration-preflight.py` 用于无外网的独立 H2 容器验证，不能运行在生产环境。
